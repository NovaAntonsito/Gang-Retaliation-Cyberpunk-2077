## 2. Layout and workflow

- `Working/GangRetaliation/` is the source of truth, stored at real in-game paths (`archive/`, `r6/`, `bin/`).
- `Distribution/GangRetaliation/<version>/` holds the built in-game tree, the zip and `RELEASE_NOTES.md`.
- The game folder is `H:\SteamLibrary\steamapps\common\Cyberpunk 2077`. To test: copy changed files from `Working/` into the matching game paths, launch, load a save.
- **Build a release:** bump `VERSION` in `build/build_release.py`, add a `## <version>` section to `CHANGELOG.md`, update `Current version:` in `README.md`, **and** the `GR-SetVersion` text in `Localization.reds` (shows at the bottom of the in-game settings screen, see section 5), then run `python -I build/build_release.py`. It compile-checks the scripts with the game's `scc.exe`, builds `Gang Retaliation V<version>.zip` and writes release notes. It never touches the game folder. The script does not check `GR-SetVersion` for you — four places to keep in sync, not three.
- **Vortex:** the staging copy is a separate copy of the mod. Deploying an update from Vortex overwrites any file edited in the game folder (`__folder_managed_by_vortex`). Copy edits into `Working/` first.
- **`modules/names.lua` is now OUR file, not a separate patch's.** [2026-11-17, Nova approved] Nova gave the ok to fold the Expanded Names lists directly into Gang Retaliation's own `names.lua` instead of keeping them as a separate Vortex patch. Copied `GangRetaliationExpandedNames`'s `names.lua` (same function logic, just the ~40-50-per-gang name/handle lists instead of the original 12-16; `titles` table unchanged) straight into `Working/GangRetaliation/.../modules/names.lua` and deployed it to the game folder, on the `RedFalcon` branch, not yet an official release. **The old rule ("never overwrite names.lua, it's Expanded Names' file") no longer applies to our own copy of this mod** — overwriting it with our own file is now correct and intentional. The separate `GangRetaliationExpandedNames` project still exists for anyone on an older Gang Retaliation version without this merge; nothing there was touched or retired.
- **WolvenKit "Install" writes `<project>.archive` over the mod's own archive.** That wiped the NEMESIS menu, journal and localization files once. The banner atlas therefore ships as its own archive, `GangRetaliationBanners.archive`. [verified]
- Zips: build with Python's `zipfile` (Compress-Archive in Windows PowerShell 5.1 writes backslash paths).
- **Our `build_release.py` now matches the functional part of what Nova's own release zip contains - fixed 2026-11-19.** [found 2026-11-19, comparing git commit `4eb2a92` byte-for-byte against the packaged 1.4.9 Nexus zip] Two kinds of difference were found: (1) cosmetic only - `Detection.reds`/`Hud.reds`/`Settings.reds`/`Spawner.reds`/`Stronghold.reds` have every `//` comment stripped in Nova's zip (confirmed zero non-comment diff lines), and `intel.yaml`/`shard.yaml` ship with CRLF line endings instead of git's LF; neither changes behavior, **still not copied, low priority.** (2) **functional - fixed:** Nova's zip ships `init.lua` with `dev = false`, while git source (and `Working/`'s own copy, intentionally) has `dev = true, -- GR_DEV_FLAG` - dev mode turns on the FPS/perf overlay, benchmark tooling, the fly hotkey, etc., none of which belongs in a build players run. `build/build_release.py`'s `transform_init_lua`/`shipped_bytes` now flip `dev` to `false` only in the zip and `Distribution/` copies (`Working/`'s own copy stays `true` for testing) - verified end-to-end, both the zip and the `Distribution/` tree now carry `dev = false`. Also fixed the same day: `check_version`/`release_notes`'s regex never actually matched this repo's `## [X.Y.Z] - date` changelog format (missing bracket handling) - a pre-existing bug unrelated to the dev-flag work, found while testing it.
- Logs: CET `print()` output goes to `bin/x64/plugins/cyber_engine_tweaks/scripting.log` (can lag until the game exits); redscript compile result in `r6/logs/redscript_rCURRENT.log`; the mod's own `GRLog(...)` lines (Spanish text) land in the game log. `spdlog` is not available from CET.

## 3. Map filter and strongholds

- **Cause of the 1.4.5 Q/E crash:** after every filter change the mod looped over all map marker widgets and called `GetScriptData()`; some markers were already freed by the game, so the native call faulted. Never touch marker script data in a loop over widgets. [verified]
- **Current design (1.4.7+):** follow Icon Framework: give our markers their own marker *variant* and let the game filter them. `intel.yaml` adds `WorldMap.GRStrongholdVariant` (enum `CPO_PingDoorVariant`), a filter group (`WorldMap.GRStrongholdFilterGroup`) and a mappin definition (`Mappins.GRStrongholdMappinDefinition`), and appends the group to `WorldMap.WorldMapCustomFiltersList` and the four zoom-level lists (`ZoomLevelImportant`, `AllMappins`, `ExtraMappins`, `SubDistricts`). [verified]
- `CPO_PingDoorVariant` is a leftover from the cancelled co-op mode that single-player never uses. Icon Framework hijacks `CPO_PingGoHereVariant`; the two do not clash. No filter group lists our variant by default. [verified]
- `gamedataWorldMapFilter` is a native enum and cannot be extended, so the group borrows an unused record, `WorldMap.RelicDeviceFilter`, as its `filterType` (Drug Dealer uses `VehicleForSaleFilter`). It must match `GRStronghold.MapFilter()` in `Stronghold.reds`. [verified]
- Behavior: nothing checked shows everything; only the GANG RETALIATION box shows only our markers; ticking others adds theirs. With nothing at all checked, our markers are hidden; accepted trade-off. [verified]
- **Icon** is chosen per marker class in `GRApplyMappinIcon` (`Stronghold.reds`), called from wraps of `BaseWorldMapMappinController.UpdateIcon`, `MinimapPOIMappinController.UpdateIcon` and `QuestMappinController.UpdateIcon`. It sets a texture part from the game's mappin icon atlas by name: strongholds use their own, intel uses `codex_glossary` (`download` was too small, `devil_horns` was the original stronghold icon). Part names that exist in that atlas include `apartment`, `danger`, `map_bounty`, `codex_character`, `asterix`, `devil_horns`, `Allow`, `GetIn`, `Distract`, `TakeControl`, class and lifepath icons. [verified for the three used]
- **World marker profile:** `CreateMappinUIProfile` is wrapped so both our marker types borrow the game's `OutpostVariant` profile in the 3D world (our variant has none of its own). [verified]
- **Map tooltip:** `WorldMapTooltipController` is wrapped (`OnInitialize`, `Reset`, `SetData`). Strongholds: title "Stronghold (gang)", description, optional gang banner. Intel markers: "<gang> intel target" title and description. Widget path used: `tooltip/tooltipFlex/mainLayout/content/mainContent`. [verified]
- **Banners:** nine gang images, 1360x575 each, laid out on a 2048x1024 half-size sheet, imported as xbm (TEXG_Generic_UI, not streamable, no mip chain), built into `gangretaliation\gui\stronghold_banners.inkatlas` with one part per lowercase gang name; displayed at 680x288 (same technique as Virtual Atelier's tooltip picture). Tools: `build/gang-logo-atlas/`. Setting `strongholdBanner` (on by default). [verified]
- **Bounty Board extended the same filter group (2026-11-21):** `WorldMap.GRBountyZoneVariant` (`CPO_PingLootVariant`, same unused-co-op-variant trick) was added alongside `GRStrongholdVariant` in `WorldMap.GRStrongholdFilterGroup` for the bounty-zone center/ring pins (`Mappins.GRBountyZoneMappinDefinition`) - this part was fine, same pattern as strongholds. [from code]
- **Bug found + fixed 2026-11-21, deployed but NOT confirmed resolved in game: GANG RETALIATION checkbox did nothing, and unchecking every box still left unrelated pins hidden (including fast travel markers).** Root cause was a different mappin - the bounty board's minimap search-radius circle (`GRBounties.AddCircle`, `Rewards.reds`) assigned it `gamedataMappinVariant.GenericRoleVariant`, a variant shared by a large number of unrelated vanilla mappins, instead of a dedicated one. Because the native map filter/collection system groups pins by variant, every `GenericRoleVariant` pin in the game got swept into whatever filter-group logic touches that variant, which is why toggling our own checkbox had no visible effect and unchecking everything still hid pins that had nothing to do with this mod. **Fix:** gave the circle its own dedicated variant, `WorldMap.GRZoneCircleVariant` (`CPO_RemotePlayerVariant` - yet another unused cancelled-co-op variant, same precedent as Door/GoHere/Loot), in both `intel.yaml` (`Mappins.GRZoneCircleMappinDefinition.possibleVariants`) and the actual runtime assignment in `Rewards.reds:AddCircle` (`data.variant`) - the live code path matters more than the tweak definition here, since `m_zoneCustom` defaults `false` and the circle normally uses vanilla's own `Mappins.DeviceMappinDefinition`, not our custom definition; only `data.variant` is unconditional. Deployed to the live game folder (just these two files, not the full History-merge working tree) 2026-11-21. **User re-tested after deploying and the symptom was still present** (fast travel still missing, unchecking everything still hides things) - this fix alone did not fully resolve it, so either there's a second contributing cause not yet found, or - more likely, per this game's native UI (confirmed with the user: there is no separate "All" tab, unchecking everything is supposed to be the show-everything baseline per this mod's own precedent above) - the player's save/session itself may already be stuck in a state the code fix can't retroactively unstick (e.g. if the native "active quick filter" got switched once historically and that state doesn't reset just because the underlying variant collision is fixed). Not yet root-caused past this point; the variant fix is still correct to keep regardless. [fix deployed, bug NOT resolved per live re-test]
- **Separate bug found 2026-11-21, reported upstream, not fixed by us: kill-bounty ("hunt") contract's tracked quest marker can be far from the actual search-zone circle/pins (not the intentional small decoy offset - genuinely unrelated locations, confirmed via screenshot).** Root-caused via the existing `GRBounties.DevGigInfo()`/`DevGigPins()` dev console commands (see section 7 for exact CET Lua invocation syntax): there are multiple live quest-type mappins tied to one gig objective; the one GR actually repositions each tick (the `marker` child, mode 1) is correctly placed, but the one the game actually tracks/displays (`GetMappinFromObjective`) is a *different*, `IsQuestAreaMappin()==true` instance stuck at the quest resource's untouched `0,0,0` placeholder - an orphaned mappin that toggling its journal entry to `Inactive` doesn't clean up, and that `DevGigPins(true)`'s proximity-based trim never reaches since it's nowhere near the real search zone. This is inside Nova's own still-WIP bounty quest-resource design (the `DevGigMode`/area-experiment dev commands show they're actively tuning this same area) - reported as [upstream issue #13](https://github.com/NovaAntonsito/Gang-Retaliation-Cyberpunk-2077/issues/13) with full diagnosis, repro, and the GenericRoleVariant fix diff above included for them to fold in. We deliberately did not attempt a redscript fix ourselves (manipulating a specific live `IMappin` instance's lifecycle directly, rather than via journal state, risked further corrupting quest state in an area that isn't ours to author). [reported, not fixed]

## 4. Intel

- Intel is `GRIntelSystem.m_values` in `Stronghold.reds`: a **persistent** list of whole numbers 0-100, one per gang, indexed by the fixed order in `GRIntelSystem.Gangs()` (Maelstrom, TygerClaws, Valentinos, SixthStreet, Animals, VoodooBoys, Wraiths, Scavengers, Barghest). Never reorder it; adding a gang at the end is safe. It saves with the save file, so loading an older save restores the older value; no way to keep intel and re-extract. [from code]
- Gains by rank: 5 regular, 10 soldier, 25 lieutenant, 50 boss; capped at 100; 100 = stronghold located. [from code]
- **Current mechanism (since 2026-11-18, chance model redesigned 2026-11-19 - see section 5 for the full writeup): loot a gang-branded "Intel Shard" from a downed member's corpse, dead or knocked out.** `TryKnockOut()` (knockout eligibility unchanged - rank-0 lottery pick per fight, `FleeCoin` roll for ranked members) and the new `TryIntelOnDeath()` (same broad eligibility, hooked into `GRDetection.OnNPCDeath` for a V-attributed kill) both funnel into `GRIntelSystem.RollForShard`, which gives the NPC an `Items.GRIntelShard_<Gang>` item (`r6/tweaks/GangRetaliation/shard.yaml`, nine records, one per gang, `GRIntelSystem.ShardRecordFor(gang)`/`IsShardRecord(tdbid)` map between them) via `GiveIntelShard`, queued 0.5s after the knockout/kill (not synchronous - see the timing bug writeup in section 5). **A named/promoted Nemesis (rank > 0) always drops it; a plain gang member rolls the configurable `GRSettings.intelDropPercent` chance (0-25%, default 10).** Looting it (`@wrapMethod(ScriptedPuppet) OnItemRemovedEvent` fires on the *source* NPC) starts the same "Extracting Intel" HUD bar as before, purely cosmetic (no interaction, no dependency on the NPC staying alive/nearby), and grants intel when the bar completes (`OnShardLooted` -> `StartShardBar` -> `OnTick` -> `AddIntel`). If the NPC is actually killed before a knockout-given shard is looted, it's silently destroyed (`OnNPCDeath` -> `DestroyIntelShard`, the "dead man's switch" - a kill before looting means no intel, but a kill *after* looting still counts). [verified in game]
- **Replaced/removed 2026-11-18, after the shard proved consistent:** the old "Extract Data" interaction (`Takedown.GRExtractData` action, `GangRetaliation.IntelTarget` status effect, added to NPC choices via a `ScriptedPuppetPS.GetValidChoices` wrap) and its own map/HUD marker (`GRIntelMappinData`, `AddMark`/`RemoveMark`/`RestoreMark`/`OnMarksTick`) are gone entirely - removed from both `Stronghold.reds` and `intel.yaml` (the shared map-marker/filter records used by Stronghold dens were kept, only the Intel-specific action/effect/mappin-data were cut). See section 5 for the full implementation and debugging history.

## 6. Things that bit us

- redscript annotations (`@wrapMethod` etc.) only work on classes from the game's own scripts, not on another mod's classes (`../Cyberpunk_Modding_Notes.txt` #12).
- A compile error in any script surfaces at game launch for all mods; check `redscript_rCURRENT.log` after edits.
- A wrapped game method that an update renames breaks compilation; keep changes small and in our own folder where possible.
- CET: `Reflection.GetClass("DismembermentComponent")` returns nil; the RTTI name is `gameDismembermentComponent`. Python on Windows needs `PYTHONIOENCODING=utf-8` when printing accented text; a here-doc can collapse backslashes (write scripts to a file).
- Replaying all markers after a filter change crashed with Icon Framework; re-invoking `OnQuickFilterChanged` cascaded through the filter list. Both were reverted; do not retry.
- Our early claim that `OutpostVariant` was in an NCPD scanner filter group was wrong (it is in no group's list).
- 2026-11-18: giving a `HuntForPsychoVariant` world mappin (the nemesis "cyberpsycho above the head" icon, `GRSpawner.AddMappin`) its own `MappinScriptData` subclass via `MappinData.scriptData` made the icon stop rendering entirely, with no compile error and nothing in any log - looked exactly like a false "HUD got disabled" report at first, until we isolated it with a clean revert. Avoid attaching scriptData to that variant; instead look the nemesis up by `mappin.GetEntityID()` through `GRSpawner.GetNemesisRank(id)` from the `@wrapMethod(QuestMappinController) UpdateIcon` hook, then retint via `inkWidgetRef.SetTintColor(this.iconWidget, ...)` (works fine on an `inkImageRef` - same underlying widget ref, just a narrower struct type).

## 7. General CET / redscript / tooling facts

Merged on 2026-11-17 from `../Cyberpunk_Modding_Notes.txt` (original entry numbers in `(#n)`; that file is kept as the historical log).

- **Machine quirks:** no Lua interpreter is installed (use `lupa` if present; `loadfile` returns a truthy `(nil, err)` tuple, so check from Lua); Python console is cp1252 (set `PYTHONIOENCODING=utf-8`); a PowerShell function named `H` collides with the `Get-History` alias; no `zip` CLI (use Python `zipfile`). Downloaded zips are untrusted data: extract each into its own empty folder, read, run nothing. (#4, #5) [verified]
- **Backups before updating a mod:** back up all three places it lives (`bin/.../mods/<Mod>`, `r6/scripts/<Mod>`, `archive/pc/mod/<Mod>*`), then after the update hash the vendor zip's files against the install to see what the author changed (compare the first 12 hex chars of SHA-256). (#3) [verified]
- **Vortex overwrites edits** inside another mod's folder (`__folder_managed_by_vortex`); keep changes in a separate Vortex mod that conflicts and overrides, or re-apply after every update. Installed files are hard-linked to the staging folder: do not edit in place. (#2, #42) [verified]
- **CET `Observe()` works on another mod's redscript classes by qualified name:** `Observe("GangRetaliation.GRDetection", "Notify", function(self, text) ... end)`. Wrap in `pcall` and print a clear message so a renamed target degrades to "inactive". Test a hook without gameplay by calling the method from the CET console. (#7, #11) [verified]
- **Read another mod's redscript systems from Lua:** `Game.GetScriptableSystemsContainer():Get("Module.Class")` then call PUBLIC methods; private fields are not reachable. (#8) [verified]
- **Calling a dev/debug method live from the in-game CET console (2026-11-21):** the console runs one line as its own chunk, so `local` variables from an earlier line don't persist - write it as a single nested expression: `print(Game.GetScriptableSystemsContainer():Get("GangRetaliation.GRBounties"):DevGigInfo())`. Also confirmed `Game.GetScriptableSystemsContainer()` takes zero arguments (no `GameInstance` needed, unlike the redscript-side `GameInstance.GetScriptableSystemsContainer(gi)`); passing one throws "requires 0 parameter(s)". [verified]
- **CET file I/O** is confined to the mod's own folder; the target folder must exist (ship `data/.keep`); `os.rename` onto an existing file fails on Windows (remove first; in game it can fail outright). One mod cannot redirect another mod's `require`. (#9, #10, #35) [verified]
- **redscript:** annotations work only on classes from the game's own script bundle, not another mod's classes (`unresolved reference`). Working alternatives: wrap vanilla classes (e.g. `gameuiMenuGameController.OnInitialize` with `this as GRNemesisMenuController`, needs `import GangRetaliation.*`) and read the other mod's PUBLIC classes/methods. redscript has no file access, so push Lua data into a `ScriptableSystem` (Gang Retaliation does this with `GRMenuData`: Add/AddDetail/AddStats/AddRumor). A compile error surfaces at launch for ALL scripts; keep companions in their own folder and pin them to a version. (#12-#14) [verified: compiles]
- **Offline compile check without launching the game** (`build/build_release.py` does this for us; the shared `../../Tools/scc_check.py` does it for the INSTALLED mod): `scc.exe -compile <root>/scripts <out.redscripts>` from the game's `engine/tools`; the first `-compile` path is treated as the game's `r6/scripts`, its parent is the root and `<root>/cache/final.redscripts` must be the vanilla bundle; extra mods go inside `<root>/scripts`. A compile error prints the full text, exits 1 and pops a Windows dialog (expected). The full 684-file set crashes `scc.exe` (stack overflow): use a MINIMAL tree: the mod plus Codeware and TweakXL scripts (`red4ext/plugins/<X>/Scripts`). Never trust "Compilation complete" alone: grep the output for your class names. (#22) [verified]
- **WolvenKit:** game 2.5 needs WolvenKit 10.x (10.0.0-beta.1 is the only 10.x so far; 9.1.1 is for game < 2.5). The installer does NOT include the command-line tool: download `WolvenKit.Console-<ver>.zip` separately (ours is in `../../Tools`); verify SHA-256 against the GitHub release digest. (#26) [verified]
- **!! WolvenKit.CLI pitfall:** `convert serialize|deserialize` and `pack` take ONLY file/folder paths. There is no `-gp` option for them; an unknown `-gp <game folder>` is taken as another INPUT PATH, so the tool walked the whole game folder and wrote 1,251 empty `X.json` files. Always run `<command> --help` first and pass nothing it doesn't list; afterwards check the game folder for strays (`find <game> -newermt "<time>"`). Pack in the system temp folder: OneDrive locks folders it syncs. (#27) [verified]
- **Adding a hub button + fullscreen menu from a separate mod** (how Gang Retaliation does it): (1) a `ScriptableService` registers Resource/Ready for `base\gameplay\gui\fullscreen\menu.inkmenu` and pushes an `inkMenuEntry {name, menuWidget = r"<mod>\gui\<x>.inkwidget"}`; (2) `@wrapMethod(MenuHubLogicController).OnInitialize` spawns `menu_button` into `mainMenu/buttonsContainer/panel_<x>` and calls `MenuItemController.Init(MenuData{fullscreenName, identifier, parentIdentifier, label, icon})`. Vanilla hub: `mainMenu/buttonsContainer/{buttons, panel_inventory, panel_journal, panel_character, ...}`; `panel_journal` children use a 170 px grid (next free slot 680); `panel_character`: stats at 330, Gang Retaliation's button at 500. (#23, #24) [verified in game]

## 8. Gang Retaliation internals (read from the 1.3.x / 1.4.x code and Nexus page)

- **Messages:** every on-screen message goes through `GRDetection:Notify(text)`. Lua queues messages and releases one every 3.5 s when `CanNotify()` is true; if the user's `notifyCenter` setting is off, `Notify` writes to the activity log instead; `Integrations.reds` also calls `Notify` directly. (#16) [verified]
- **Campaign ID:** a persistent Int32 in `GRSystem` (random 100000..999999999), `GRSystem:GetCampaignId()`. (#17) [verified]
- **Save data:** `data/gang_retaliation.json`, `campaigns[<id>].nemeses[]` with fields including name, titleEn, titleEs, gang (key), rank, status, renown, origin, traits. Dead nemeses STAY in the list. Gang keys: Maelstrom, TygerClaws, Valentinos, SixthStreet, Animals, VoodooBoys, Wraiths, Scavengers, Barghest (display labels differ: "6th Street", "Scavs", ...). (#18) [verified]
- **Names (`modules/names.lua`):** draws up to 30 random names looking for one unused by ANY nemesis of that gang in that campaign (dead included); only if all 30 collide does it add a numeral II..X. `maxPerGang` (default 8, max 12) limits living nemeses only. No two gangs can generate the same name, so (campaign, gang, exact name) is unique. A nemesis's TITLE changes when it returns from the dead, so titles are not an identity key. Original pools are small (12-16 names for some gangs); the Expanded Names patch raises every list to ~40-50. Stock `names.lua` SHA-256 prefix `8E5824FFE82B` (1.3.3 to 1.4.0); the 1.4.5 file has the same md5 `f674e861...` as before. (#19, #20, #42, #51) [verified]
- **`GRMenuData:GetEntries()`** is public and returns each nemesis (gang, name, title, rank, dead, renown, traits, encounters, escapes, ambushes, gigs, origin, cause) but no nemesis ID; refreshed only when the main mod pushes its menu data. 1.4.5 adds `GRMenuData.RequestView(gi, view)` (one-shot, call right before opening `gangretaliation_nemesis_menu`) and `OpenView(from, view)`. (#21, #48, #49) [from code]
- **Boss weapons (1.4.0):** a vanilla item renamed "{boss}'s {weapon}" (boss = display name incl. title, weapon = the game's item name), built in `Rewards.reds` `FormatName`. 1.4.0 also added `Rewards.reds` and `Stronghold.reds`, the Arsenal / weapon augment screen (`Menu.reds`), Barghest raids, strongholds and machine-NPC exclusion. (#42, #43) [from code]
- **Message keys** used by companions: `GR-MsgRaidBarghest`, `GR-MsgBarghestEscape`, `GR-MsgStrongholdCleared`, `GR-MsgBossWeapon`, `GR-IntelGained`, `GR-IntelLocated`. (#42, #51)
- **Nexus page** (https://www.nexusmods.com/cyberpunk2077/mods/36235, read 2026-11-11 at v1.3.4): tagged "AI Assisted". Requirements: Cyberpunk 2077 2.5, Cyber Engine Tweaks 1.38, RED4ext 1.31+, redscript 0.5+, Codeware 1.21+, ArchiveXL 1.28+, Mod Settings 0.2.25+, TweakXL 1.12+. Optional integrations: They Will Remember, Drug Dealer. (#31) Permissions are summarized in `../GangRetaliationHistory/NOTES.md` section 5.
- **Localization:** the main mod uses a Codeware `ModLocalizationProvider` with English and Spanish packages (`Localization.reds`). (#33)

- **How a nemesis gets its look** [from code, read 2026-11-15; Detection.reds, hierarchy.lua, ambush.lua, cyberlooks.lua, Spawner.reds]: a nemesis stores the NPC `recordID` and `appearance` (plus gender and health). A new nemesis is made from the NPC that escaped (`MakeCandidate` in `Detection.reds` copies their record and appearance). Recruits to a gang are random picks from `Escorts[gang]` (`hierarchy.lua` `recruit`). A nemesis that returns from the dead gets `CyberLooks.apply` (a tier 2/3 record of the same gender). `SpawnAt` uses the stored `appearanceName`, or `"random"` when none; `processAppearances` stores the appearance that was actually spawned. Ambush escorts are random records chosen by rank (1 / 2 / 4). Gang membership is decided by `record.Affiliation()`; machines are filtered with `IsMachineRecord`.
- **Injuries are not tracked per body part** [from code]: only `DeathKind` (`Spawner.reds`) uses `GetDismemberedLimbCount()` (flesh + cyber > 0 gives "confirmed", no return chance). `n.health` is stored at escape but not used when spawning. "Wounded" only exists as the message `GR-MsgEscaped` and the origin label `GR-Origin-escaped`; no limb or body-part data is kept.
- **Custom looks (ACM / Appearance Menu Mod)** [from code + idea, untested]: AMM changes live NPCs with `ChangeAppearanceTo`, uses `DynamicEntitySystem` and creates records at runtime with `TweakDB:CloneRecord` (`AMM_Character.*`); ACM installs as empty folder shells here. Custom looks could be used by adding their appearance names to the gang's `Escorts` / `CyberLooks` pools (the stored `appearance` is just a name passed to spawn). Nothing built or tested.
- **Night City Remembers (Nexus 29008, 3.9.0) compatibility** [from code, untested in game]: no method collisions with Gang Retaliation (it wraps different vanilla methods); the risk is gameplay overlap (two mods reacting to the same kills / bounties), not compile errors.
- **Compile-testing against an API that is not installed yet:** `@addMethod` on another mod's class is rejected (`INVALID_ANN_USE`), so stub it by editing a scratch copy of that mod's file (add the function to its class in the scratch tree), not with an annotation. Worked for `GRMenuData.RequestView` before 1.4.5 existed. `build/build_release.py` of the History mod fails its pre-flight against an older main mod for the same reason; `--skip-checks` builds anyway (only use it when you know why).
